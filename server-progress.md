### Gotchas hit & fixed

1. **`generate_config.sh` partially fails on macOS** — uses Linux-only `/proc/meminfo` and GNU `cp -d`,
   neither of which exist on macOS. The script still produces a usable `mailcow.conf`, but the
   self-signed cert files (`cert.pem`, `key.pem`, `dhparams.pem`) it generates are never copied into
   `data/assets/ssl/` because the `cp -d` step silently fails.
   Fix: manually `cp data/assets/ssl-example/{cert,key,dhparams}.pem data/assets/ssl/`. Missing
   `dhparams.pem` specifically crashes Dovecot on every start (`ssl_dh: Can't open file ... No such
   file or directory`) until copied.
2. **Same hostname/domain collision as Phase 0** — avoided this time by using `mail.local.test` for the
   server and `local.test` for the mailbox domain from the start.
3. **`doveadm auth test` reports auth failure even with a correct password** — this is a CLI-testing
   artifact: Mailcow's Dovecot auth backend is a Lua script that calls an internal HTTP endpoint
   (`mailcowauth.php`) requiring a `real_rip` field that `doveadm auth test`'s synthetic connection
   doesn't populate, so the request comes back `400 Bad Request`. Not a real login failure — confirmed
   by testing an actual IMAP connection (Python `imaplib`), which logged in and read the mailbox fine.
4. **SOGo webmail login fails (`403`, `LDAPPasswordPolicyError`) even with correct credentials** —
   two layered issues found: (a) SOGo's per-domain auth config (`/var/lib/sogo/GNUstep/Defaults/sogod.plist`)
   is generated once at container startup by `bootstrap-sogo.sh`, which ran before the `local.test` domain
   existed, so it initially had zero domains configured (fixed by restarting the `sogo` container after
   adding the domain). (b) After that fix, SOGo's actual auth source — a MariaDB table called
   `_sogo_static_view` — still holds a stale placeholder password hash (`SSHA256` of an empty string) for
   `admin@local.test` instead of the real one, even after resetting the mailbox password via the API.
   Root cause not fully isolated (not a DB trigger — `SHOW TRIGGERS` on `mailbox` is empty); likely an
   artifact of this being a fresh `--depth 1` clone on macOS rather than an official Linux install.
   **Not blocking**: IMAP/SMTP/API access all work correctly; only the SOGo web UI is affected. Re-check
   after `./update.sh` or once running on the real Linux VPS before treating this as a real bug to fix.

### Mailcow REST API — verified working endpoints

Base: `https://<host>/api/v1/`. Auth: header `X-API-Key: <key>`. Local dev key generated directly via
SQL (`INSERT INTO api (api_key, allow_from, skip_ip_check, access) VALUES (...)`) since scripting the
JS-driven admin UI login was more fragile than just using the interface the dashboard app will actually use.

| Action | Method | Endpoint | Notes |
|---|---|---|---|
| Add domain | POST | `/add/domain` | Auto-generates a DKIM key as a side effect |
| Add mailbox | POST | `/add/mailbox` | `local_part` + `domain` + `password`/`password2` |
| Edit mailbox (e.g. reset password) | POST | `/edit/mailbox` | `items: [email]`, `attr: {...}` |
| Get DKIM record | **GET** | `/get/dkim/<domain>` | Returns `dkim_txt` (full record) + `dkim_selector` — POST returns 405, must be GET |

Full request/response examples: see `FLOW.md`.

## Phase 2 — VPS Migration (repo ready, VPS deploy pending)

Naming decision: the mail engine itself lives on **`mail-engine.<domain>`** — kept deliberately
separate from both the customer-facing product (`domain.com` frontend, `api.domain.com` backend,
future separate project) and from the actual email domain(s) customers use (`someone@domain.com`).
This is the same hostname/mailbox-domain separation gotcha from Phase 0/1, just with a more explicit
name this time.

### Repo structure for deploy

`mailcow-dockerized/` is **not** committed to this repo (see `.gitignore`) — it's a large upstream
project with its own git history, and `generate_config.sh` writes secrets (DB/Redis passwords, API
keys) into `mailcow.conf` plus self-signed certs into `data/assets/ssl/`. None of that belongs in
version control. Instead, `scripts/deploy-vps.sh` clones it fresh on the VPS and configures it.

### VPS deploy steps

- [ ] Add DNS records first: `A` record `mail-engine.<domain>` → VPS IP; `MX` record `<domain>` →
  `mail-engine.<domain>`, priority 10
- [ ] On the VPS: `git clone <this-repo>`, then `./scripts/deploy-vps.sh mail-engine.<domain>`
  (script clones Mailcow, runs `generate_config.sh`, leaves Let's Encrypt **enabled** this time since
  real DNS is live — opposite of local dev — and starts the stack)
- [ ] Open required ports (25, 465, 587, 143, 993, 110, 995, 80, 443) + firewall (UFW/Fail2Ban)
- [ ] Provision the real domain + a test mailbox via the same API calls verified in `FLOW.md`
- [ ] Fetch the real DKIM record, add SPF/DKIM/DMARC TXT records, then run
  `scripts/verify-domain-dns.sh <domain> mail-engine.<domain>` to confirm all pass for real
- [ ] Re-verify SOGo webmail login on the real install (expect gotcha #4 above to not reproduce)
- [ ] Real send/receive test: VPS mailbox → external Gmail, and Gmail → VPS mailbox
- [ ] Set up daily backups
